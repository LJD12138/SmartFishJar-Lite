# APP UI 实施计划

## 1. 文档目的
基于现有 UI 设计资料，形成一份可直接指导 `APP` 工程落地开发的实施计划，确保 OLED UI 能从当前测试页平滑演进为正式业务界面。

本计划聚焦以下目标：
- 将当前 `WORK` 态测试显示替换为正式页面体系。
- 按既定状态机落地 `INIT / BOOTING / WORK / CLOSING / SHUT_DOWN / ERR / UPDATA` 显示流程。
- 建立统一的页面模型、按键模型、刷新策略和告警展示机制。
- 控制改造范围，优先复用现有显示任务与队列结构，避免大范围扰动业务逻辑。

## 2. 设计输入依据
本计划依据以下资料制定：
- `APP_UI_设计说明.md`
- `APP_UI_布局总览.csv`
- `APP_UI_页面明细.csv`
- `APP_UI_运行细则.csv`
- `APP_UI_开发任务拆解表.md`
- `APP_UI_周计划_甘特排期表.md`

## 3. 当前实现基线
结合现有代码，当前显示链路具备较好的基础，但正式 UI 仍未完成：

### 3.1 已具备基础
- 已有显示总任务与队列调度框架。
- 已按设备状态拆分显示队列任务：`init / booting / work / err / closing / shut_down / updata`。
- 底层 OLED 驱动已切至 `u8g2` 路径。
- 已存在全局显示状态与页面脏标志：`tDisp`、`g_bDispPageDirty`。
- 已有自动息屏、亮屏控制、设备状态切换能力。

### 3.2 当前主要缺口
- `WORK` 态显示仍调用 `vDisp_UiTest()`，未接入正式页面模型。
- 页面 ID、焦点 ID、弹层模型、底部提示尚未结构化。
- 按键语义与页面切换规则尚未形成统一实现。
- 页面局部刷新、告警映射文本、设置页缓存/保存机制未成体系。
- 设计文档中的 `HOME / ENV / ACT / ALARM / SETTING / QUICK` 尚未代码化。

## 4. 实施范围
### 4.1 本次纳入范围
- `APP` 工程 OLED 正式 UI。
- 页面状态机、工作页导航、弹层、告警页、升级页、关机页、息屏页。
- 与 UI 直接相关的按键处理、刷新策略、参数编辑与状态展示。
- 文本映射、图标占位、局部刷新机制。

### 4.2 本次不纳入范围
- `BOOT` 工程业务 UI 重构。
- 与 UI 无关的底层驱动重写。
- 未启用模块（如 `DC / USB / ENG_MODE`）的正式业务页面。
- 高级动画、复杂图标美化、主题化样式系统。

## 5. 实施原则
1. **先通流程，再补细节**：优先打通状态页与核心工作页，再补设置页与优化项。
2. **保留现有任务结构**：尽量不推翻 `md_display_queue_task_*` 现有组织方式。
3. **统一页面模型**：所有页面都通过统一枚举、绘制入口和焦点管理驱动。
4. **按键行为全局一致**：避免同一按键在不同页面出现不可预期含义。
5. **先整页正确，再做局刷优化**：先保证内容准确，再减少闪烁与刷新开销。
6. **业务状态只读优先**：UI 先做“展示准确”，控制项再逐步接入写操作。

## 6. 总体实施阶段
建议分 4 个阶段推进，总工期建议为 **8~12 人天**。

| 阶段 | 目标 | 主要输出 | 预估工时 |
| --- | --- | --- | --- |
| 阶段 A | 搭建 UI 框架骨架 | 页面枚举、焦点模型、统一绘制入口、按键分发入口 | 1.5~2 人天 |
| 阶段 B | 交付核心页面闭环 | `BOOTING/HOME/ALARM/UPGRADE/CLOSING/SLEEP/ERROR` 可运行 | 2.5~3.5 人天 |
| 阶段 C | 交付工作态完整交互 | `ENV/ACT/SETTING/QUICK` 与参数编辑能力 | 2.5~3 人天 |
| 阶段 D | 优化与联调验收 | 局刷优化、文本完善、异常回退、验收测试 | 1.5~2.5 人天 |

## 7. 分阶段实施计划

### 阶段 A：UI 框架搭建
目标：建立正式 UI 可持续扩展的代码骨架，替换测试页依赖。

#### A.1 代码结构调整
建议在 `Hardware/MD_Display` 下补充或重构为以下职责层：
- `md_display_page.h/.c`：页面 ID、焦点 ID、页面上下文、页面切换逻辑。
- `md_display_draw.h/.c`：统一绘制入口、状态栏/主体/底栏公共绘制函数。
- `md_display_key.h/.c`：按键到 UI 动作的映射与分发。
- `md_display_text.h/.c`：错误码、页面名、状态名、底部提示文本映射。
- `md_display_icon.h/.c`：图标位图或图标绘制封装。

> 若希望改动更小，也可不新建过多文件，而是在现有 `md_display_api.*` 中先抽出最小可用的 `page + draw + key` 三层。

#### A.2 需优先定义的核心对象
建议先建立以下基础结构：
- `DispPageId_E`：页面枚举。
- `DispOverlayId_E`：弹层/覆盖层枚举。
- `DispFocusId_E`：当前页焦点项枚举。
- `DispPageCtx_T`：当前页面、来源页、焦点、编辑态、弹层态。
- 页面底部提示：用于页面下方提示显示。
- `DispDirtyMask_T`：整页/局部区域脏标志。

#### A.3 阶段验收标准
- `WORK` 态不再直接依赖 `vDisp_UiTest()` 作为唯一显示入口。
- 已能根据 `tDisp.eDevState` 进入统一页面调度逻辑。
- 页面切换、焦点切换、弹层显示具备基本数据结构支撑。

### 阶段 B：核心状态页闭环
目标：优先交付对用户最关键的“开机可看、异常可看、升级可看、关机可看”。

#### B.1 优先落地页面
按设计要求，优先实现：
- `P01_BOOTING`
- `P10_HOME`
- `P13_ALARM`
- `P20_UPGRADE`
- `P21_CLOSING`
- `P22_SLEEP`
- `P23_ERROR`

#### B.2 代码落点建议
- `md_display_queue_task_booting.c`：负责启动页动画与自检状态拼装。
- `md_display_queue_task_work.c`：接入 `HOME/ALARM` 页面调度，不再只显示测试页。
- `md_display_queue_task_err.c`：接入严重错误覆盖显示。
- `md_display_queue_task_updata.c`：按升级阶段和百分比刷新升级页。
- `md_display_queue_task_closing.c` / `md_display_queue_task_shut_down.c`：关机与息屏页按设计规范统一显示。

#### B.3 重点实施内容
- 建立 `状态栏 8px + 主体 40px + 软键区 16px` 固定模板。
- 建立 `Error/Alarm` 文本映射表，实现“错误码 + 短说明 + 建议动作”。
- 建立 `HOME` 首页摘要区，至少显示：
  - 水温 / 目标温度
  - 灯光状态
  - 氧泵 / 水泵 / 加热状态
  - 告警摘要
- 建立 `SLEEP` 唤醒规则：首个唤醒键仅亮屏，不透传功能。

#### B.4 阶段验收标准
- 上电后可按 `INIT -> BOOTING -> HOME` 正常进入首页。
- 有普通告警时可查看 `ALARM` 页，有严重错误时可覆盖显示 `ERROR` 页。
- 进入升级模式时只能显示升级页，普通 UI 操作被锁定。
- 长按 `Enter` 进入关机流程时，显示页与状态切换一致。

### 阶段 C：工作页完整交互
目标：把工作态页面从“可看”推进到“可操作”。

#### C.1 需实现页面
- `P11_ENV`
- `P12_ACT`
- `P12A_QUICK`
- `P14_SETTING`

#### C.2 重点实施内容
1. **ENV 页面**
   - 展示水温、环境温度、光照、12V 状态。
   - 支持字段焦点切换与更新时间显示。

2. **ACT 页面**
   - 管理灯光、氧泵、水泵、加热对象。
   - 支持对象切换、开关确认、亮度/模式调整。

3. **QUICK 弹层**
   - 从 `HOME/ACT` 通过 `Enter 短按` 或 `Right 长按` 呼出。
   - 高亮 3 项快捷对象：灯光 / 氧泵 / 水泵。
   - 保证退出后回到来源页，不丢失上下文。

4. **SETTING 页面**
   - 支持息屏时间、蜂鸣器、亮度高低档、恢复默认。
   - 实现“编辑缓存”和“确认保存”分离机制。
   - 保存成功给出一次性提示，保存失败给出错误反馈。

#### C.3 阶段验收标准
- `Left/Right` 可在 `HOME / ENV / ACT / ALARM / SETTING` 间循环切页。
- `Up/Down/Enter` 在工作页语义与设计文档一致。
- 参数修改未确认前不落 Flash，确认后才持久化。
- 快捷弹层可稳定打开、执行、退出。

### 阶段 D：优化、联调与验收
目标：降低闪烁、补齐边界处理、完成交付验证。

#### D.1 优化项
- 整页刷新与局部刷新分离。
- 数值变化只刷新必要区域。
- 软键栏只在页面切换或焦点变化时更新。
- 启动/升级页按 100~200ms 节奏刷新。
- 普通数据页按 250~500ms 节奏刷新。

#### D.2 联调项
- 与按键模块联调长按/短按识别。
- 与参数存储模块联调保存与恢复默认。
- 与告警/错误管理模块联调错误码映射。
- 与各执行器模块联调状态读取与控制反馈。

#### D.3 阶段验收标准
- 局部刷新可明显降低工作页闪烁。
- 无操作自动息屏、唤醒恢复、异常覆盖、升级锁屏均符合设计规则。
- 所有一级页面均可进入，主要路径无死循环、无卡页、无错误回跳。

## 9. 关键依赖清单
UI 实施依赖以下业务数据与能力：

### 9.1 数据读取依赖
- 水温、环境温度、目标温度。
- 光照值、灯光模式与亮度。
- 氧泵、水泵、加热模块开关与运行状态。
- 12V 输入状态。
- 当前错误码、告警级别、告警数量。
- 升级流程阶段与百分比。

### 9.2 配置写入依赖
- 息屏时间。
- 蜂鸣器开关。
- 亮度高低档。
- 恢复默认参数。

### 9.3 输入事件依赖
- `Enter / Left / Up / Down / Right` 短按。
- `Enter / Left / Right` 长按。
- 息屏状态下任意短按唤醒。

## 10. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 现有业务状态分散，UI 取数口径不统一 | 页面内容不稳定、联调反复 | 先建立统一 UI 读模型，集中封装状态采样 |
| 按键短按/长按边界不清 | 误触发翻页、误关机 | 先与按键模块确认事件层，不在 UI 层重复识别时序 |
| 页面切换与严重错误覆盖互相打断 | 出现卡页或回退异常 | 统一来源页与覆盖页优先级模型 |
| 局刷策略过早引入 | 提高复杂度、增加显示 Bug | 先整页跑通，再逐步引入局部刷新 |
| 设置页直接写 Flash 过频 | 影响寿命、交互迟滞 | 采用缓存编辑，确认后一次写入 |
| 文本过长超出 128x64 | 截断、重叠、可读性差 | 先定义固定文案长度与缩写规则 |

## 11. 验收测试建议
建议按“状态流 + 页面流 + 交互流 + 异常流”四类开展测试。

### 11.1 状态流测试
- 上电进入初始化、启动、自检、首页。
- 长按关机进入关机页并熄屏。
- 息屏后任意短按唤醒回上次页面。
- 升级模式下只能停留升级页。

### 11.2 页面流测试
- `HOME -> ENV -> ACT -> ALARM -> SETTING -> HOME` 循环切换正常。
- 快捷弹层可从 `HOME/ACT` 正常进入与退出。
- 错误覆盖页解除后可返回来源页或首页。

### 11.3 交互流测试
- `Up/Down` 改值、`Enter` 确认、`Left/Right` 翻页行为一致。
- 设置页编辑缓存与保存落盘符合设计规则。
- 首次唤醒键不透传功能。

### 11.4 异常流测试
- 传感器失联时状态栏和告警页同时给出提示。
- 严重错误时优先覆盖普通页。
- 保存失败、升级失败、读取异常时有可理解文案。

## 12. 建议交付物
实施过程中建议同步交付以下产物：
- 正式 UI 代码。
- 页面/错误码/软键文案映射表。
- 页面切换状态图。
- UI 联调检查单。
- UI 验收记录表。

## 13. 建议实施顺序总结
建议严格按以下顺序推进：
1. 搭页面模型与统一绘制入口。
2. 替换 `WORK` 测试页为正式调度框架。
3. 先交付 `BOOTING/HOME/ALARM/UPGRADE/CLOSING/SLEEP/ERROR`。
4. 再补 `ENV/ACT/QUICK/SETTING`。
5. 最后做局刷、图标、提示文案和边界优化。

## 14. 结论
本次 UI 实施不建议一次性“大改重写”，而应基于现有 `MD_Display` 任务框架，采用“**页面模型补齐 + 工作页替换 + 核心页先落地 + 交互后补齐 + 最后优化**”的方式推进。

这样可以在较低风险下，先尽快把“用户可见、可用、可验证”的正式 UI 交付出来，并为后续图标、动画、工程模式扩展留下稳定基础。
